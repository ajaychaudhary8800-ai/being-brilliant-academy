## New independent, non-deploying development

`.github/workflows/schoolos-v5-prior-oci-candidate-ephemeral.yml` runs only for an in-repository PR changing this workflow or its exact two helper files, on a branch starting `security/schoolos-v5-phase1-clean-oci-`; forks do not qualify. It uses a disposable GitHub-hosted Ubuntu runner (not the owner server), checks out audited controls at exact PR head and historical V5 source commit `b54dca5ae36a948f83012faa4a37354198fba083`. No environment/R2/Docker secrets from staging/production are provided to the build. A one-line Dockerfile modification excludes only pinned public dependency example documentation from the previous API's inherited dependency context, preserving Git source and package lock; the precise original Dockerfile and prune helper blobs are independently hash-pinned. **The derived API build is not certified byte-identical to the historical deployed binary.**

In an isolated ephemeral Buildx environment, CI builds two fresh Linux/amd64 OCI image-layout archives using `--output type=oci`, with only the public source SHA and public relative API path supplied as build args. It disables auxiliary attestation and SBOM manifest generation for a single-index-OCI verifier contract. Outputs remain private to disposable `$RUNNER_TEMP` and are removed at job end. The workflow explicitly has no `upload-artifact`, registry login, R2 writer, `docker push`, staging/production SSH or deployment steps.

`scripts/schoolos-v5-prior-oci-candidate-manifest.py` independently checks the resulting real OCI TARs with the existing strict offline OCI implementation: full file SHA256/size, actual one-index OCI manifest descriptor and blob hashes, Linux/amd64 and pinned previous source label, all referenced compressed layer hashes/sizes and decompressed plain/gzip rootfs DiffIDs, no extra referenced/unreferenced blobs and no unsafe TAR members. It additionally rejects sensitive key assignments within image config environment, image labels, and image history using fixed predefined key names (no sensitive values printed). This is **bounded metadata name-pattern screening**, not semantic secret or vulnerability clearance of every filesystem-layer payload. It never reads private R2, contacts Docker directly, signs images or exports private content to logs.

It writes **one private 0600 unsigned draft JSON** with the exact `schoolos-v5-private-rollback-readback-v1` schema, under the ephemeral runner's temporary directory only. Fields record the pinned previous source SHA, each archive's complete tar checksum, byte length, actual OCI image manifest digest and planned `v5-rollback/<sha>/{api,web}.oci.tar` object keys. This helper does not sign or publish anything. A GitHub OIDC `actions/attest@v4` step signs the **receipt file as a CI subject**, with storage record creation disabled. **Do not confuse the signed receipt with independently witnessed clean source-to-build provenance, signed OCI image manifests, private object retention, actual images leaving the runner, or rollback readiness.** GitHub Actions may retain generic execution logs and the receipt attestation; it does not retain the OCI image archives.

## Acceptance and hard stop

- A passing end-to-end job, if it occurs, proves ephemeral **candidate creation with actual OCI content checks**, at that exact source and controls commit, and a signed receipt observation. It does **not** produce a retrievable image pair or fulfill rollback custody #292.
- Before actual private publication, an independent operator must review **actual** image content including semantically sensitive rootfs files, baseline dependencies, builder/source provenance, old-source recipe differences, fixed signer/public-key pin, and separate R2 publisher/reader credentials with narrow permissions. Only after that review should the trusted clean archives be privately exported through an approved custody mechanism—not into GitHub artifacts or chat.
- Then independently verify 90-day R2 lock on the expected prefix (owner control plane `PASS_CONFIGURATION_ONLY`), actual object bytes under that lock and a separate read identity, private pinned detached signature, actual OCI manifest digest, and application recovery against a *real* isolated backup with DB/files/Vault/media.
- Incident #293 PostgreSQL/Redis historical credentials remain exposed to previous archive holders until maintenance rotation with verifiable old-password rejection and secure app/DB/key continuity. Incident #281 runtime-scoping acceptance is separate. #258 formal release gates remain 0/10.

CI always emits `DEPLOYMENT_AUTHORIZATION=HOLD`. Never interpret a CI receipt as authorization for credential rotation, source promotion, production change or customer billing.

## CI extension: bounded OCI *filesystem content* scan (same PR, no image upload)

After the first real CI run built both actual OCI TARs successfully and the candidate manifest checked their full OCI integrity, the isolated pipeline was strengthened to reuse existing `scripts/schoolos-v5-ci-layer-payload-audit.py` in strict `--docker-save-stdin --require-no-dependency-pem` mode **against both OCI TARs** (not only Docker-save archives). That script already supports OCI blobs and compressed layer-stream TARs; it reads each layer's payload without extracting to disk and rejects private path patterns, CI credential canaries, nonfixture dependency PEM artifacts and application-owned private PEM material. The existing OCI integrity checker separately verifies the content-addressed manifest/config/layer digests and rootfs DiffIDs. An explicit `V5_PRIOR_OCI_BOUNDED_ROOTFS_PATTERN_AUDIT=PASS_NOT_FULL_SEMANTIC_CLEARANCE` is emitted only if **both** layer scans exit zero.

The scan **does not** certify all possible plaintext secrets, malicious packages, binaries, vulnerabilities, source-to-build independent attestation, or whether ephemeral OCI candidate bytes will ever be retained. Known-name metadata scanning plus bounded filesystem patterns are helpful independent controls, not a broad cryptographic cleanliness certificate. GitHub Actions image TARs are still deleted at job exit; all deployment/rotation/R2 gates remain HOLD.
